# Full Project Development Requirements – Hotel & Flight Travel Reservation System

## 1. Role and Development Approach

Act as a Senior Software Engineer, Solution Architect, UI/UX Designer, and DevOps Engineer.

I want to develop a complete **Hotel and Flight Travel Reservation System** with a modern, professional, responsive user interface and a production-ready backend architecture.

The application should be understandable to junior developers. Write clean, maintainable, well-structured code. Avoid unnecessary complexity, overengineering, and redundant technologies.

Follow these principles:

- Analyze the existing project structure before making changes.
- If the repository already contains code, understand the existing implementation before modifying anything.
- Do not break existing functionality or business logic.
- Do not replace working implementations without a clear technical reason.
- Build reusable components and services.
- Follow industry-standard coding practices, validation, exception handling, security, and logging.
- Implement actual frontend and backend functionality. Do not create UI screens with hardcoded data and pretend the features are complete.
- Complete the project incrementally and verify each module before moving to the next.
- Maintain project documentation throughout development.

## 2. Project Objective

Develop a web-based Hotel and Flight Travel Reservation System where customers can:

1. Search and book domestic and international flights.
2. Search and reserve hotels.
3. View flight and hotel details.
4. Compare prices and available options.
5. Manage flight and hotel reservations.
6. Make online payments.
7. Download booking confirmations and invoices.
8. Cancel reservations based on applicable cancellation policies.
9. View booking history.
10. Manage their profile and travel preferences.
11. Receive booking, payment, cancellation, and travel notifications.

The system should also provide administrative portals to manage users, hotels, flights, reservations, payments, offers, reports, and system configurations.

### Flight Details

- Flight itinerary.
- Airline information.
- Departure and arrival details.
- Transit information.
- Baggage allowance.
- Fare rules.
- Cancellation and rescheduling policies.
- Additional charges.

### Passenger Information

Collect:

- Passenger type.
- First name.
- Last name.
- Date of birth where required.
- Gender where required by supplier.
- Nationality where required.
- Passport details for international travel when required.
- Contact email.
- Contact mobile number.

Do not collect passport or other sensitive information unless it is required for the selected booking and supplier workflow. Protect sensitive information at rest and in transit.

### Flight Booking Workflow

Implement the following workflow:

1. Customer searches for flights.
2. Backend retrieves available flight options.
3. Customer selects a flight.
4. Backend revalidates the selected fare and availability with the supplier.
5. Customer enters passenger details.
6. Display fare breakdown and applicable policies.
7. Customer confirms the booking details.
8. Create a temporary booking or reservation record.
9. Initiate payment.
10. Confirm the booking with the supplier at the correct stage of the supplier's booking workflow.
11. Save the supplier confirmation reference.
12. Update the booking status.
13. Generate an e-ticket or booking confirmation when available.
14. Send email and in-app notifications.

Important:

- Do not assume that selecting a flight means a seat is reserved.
- Do not assume that successful payment means the airline has confirmed the booking.
- Handle supplier timeouts, payment failures, duplicate requests, and uncertain booking outcomes.
- Implement idempotency for booking and payment operations.
- Reconcile payment and supplier booking status when the outcome is uncertain.
- Never display a confirmed ticket until supplier confirmation is received.

Implement:

- API timeout handling.

- Response mapping.
- Error normalization.
- Provider health monitoring.

Implement clear booking states, for example:

- INITIATED
- PENDING_PAYMENT
- PAYMENT_SUCCESS
- SUPPLIER_PENDING
- CONFIRMED
- FAILED
- CANCELLATION_PENDING
- CANCELLED
- REFUND_PENDING
- REFUNDED

Adjust states to support the actual supplier and payment workflow.

Important requirements:

- Prevent duplicate bookings.
- Prevent duplicate payment processing.
- Handle concurrent room reservations.
- Revalidate price and availability before final confirmation.
- Apply reservation expiry rules.
- Handle supplier API timeouts and uncertain outcomes.
- Maintain booking status history.
- Reconcile payment and supplier booking states.
- Do not mark a booking as confirmed without confirmation from the relevant inventory source.
- Never calculate the final payment amount using untrusted frontend values.

## 35. Important Development Rules

1. Do not generate only frontend UI screens. Implement the complete backend functionality.
2. Do not use hardcoded data as if it were live flight or hotel availability.
3. Demo data must be clearly identified as demo data.
4. Do not fake successful bookings or payments.
5. Do not bypass supplier confirmation.
6. Do not trust frontend prices or payment status.
7. Do not expose database entities directly.
8. Do not put business logic in controllers.
9. Do not duplicate business logic across modules.
10. Do not introduce unnecessary technologies.
11. Do not break existing functionality.
12. Use meaningful class, method, variable, and API names.
13. Implement proper validation and exception handling.
14. Add tests for important business rules.
15. Use database transactions where required.
16. Use idempotency and concurrency protection for booking and payment workflows.
17. Keep secrets outside source code.
18. Ensure the application is responsive on mobile, tablet, and desktop.
19. Do not mark a feature as complete until it has been implemented and tested.
20. Update documentation whenever architecture, APIs, or business workflows change.
